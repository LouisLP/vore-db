# vore-db

A reference encyclopedia of world foods and drinks. One row = one canonical dish or
ingredient. See issue #1 for the shape of the effort.

- `frontend/` — Vue 3 + Vite + Pinia (scaffolded, untouched by the schema work)
- `backend/` — Drizzle schema and migrations (TypeScript, pnpm)
- `docker-compose.yml` — local Postgres

## Local database

Postgres **18.1** (`postgres:18.1-alpine`), published on host port **5433** so it does not
collide with a system Postgres on 5432. Data lives in the named volume `vore-db_vore-db-data`.

Credentials live in a single `.env` at the repo root, read by both Docker Compose and
drizzle-kit. It is gitignored; `.env.example` is the committed template.

```sh
cp .env.example .env      # first time only
docker compose up -d --wait   # start Postgres, wait for the healthcheck
docker compose ps             # status
docker compose logs -f postgres
docker compose down           # stop, keep data
docker compose down -v        # stop and delete the volume (destroys the database)
```

A psql shell inside the container:

```sh
docker compose exec postgres psql -U vore -d vore
```

## Migrations

Run from `backend/`. The schema is authored in `backend/src/db/schema.ts`; generated SQL
lands in `backend/drizzle/` and is committed.

```sh
cd backend
pnpm install
pnpm db:generate   # diff schema.ts against the migration history, write a new .sql
pnpm db:migrate    # apply pending migrations to the running container
pnpm db:check      # print server version + tables in `public` — confirms what landed
pnpm db:seed       # truncate, then load the reference data and ten sample items
pnpm db:verify     # assert the model against the seed; exits non-zero on any failure
pnpm db:studio     # browse the database in Drizzle Studio
pnpm type-check
```

From nothing to a populated, checked database:

```sh
docker compose up -d --wait
cd backend && pnpm install && pnpm db:migrate && pnpm db:seed && pnpm db:verify
```

### What is in `backend/drizzle/`

- `0000_init.sql` — generated by drizzle-kit from `src/db/schema.ts`. Ten tables, two
  enums, the constraints and indexes.
- `0001_triggers.sql` — **hand-written**, created with `drizzle-kit generate --custom` so
  it sits in the journal like any other migration. It holds the three rules drizzle-kit
  cannot express: every item having at least one `origin` country (a deferred constraint
  trigger, checked at `COMMIT`), an alias never restating its item's own name, and
  `updated_at` maintenance. It also makes the image-ordering constraint deferrable.

Running `pnpm db:generate` after editing `schema.ts` will not touch `0001`, but it also
will not notice if a schema change invalidates a trigger — read the file when you change
`item`, `item_country` or `item_name`.

### Seed and verification

`pnpm db:seed` is destructive and idempotent: it truncates every table and reloads all 249
ISO 3166-1 countries, six media licences, a fifteen-node taxonomy and ten items chosen to
stress the model — multi-country origins with no primary country, native scripts with
romanisations, a three-level category, a dual-nature item, an item with no aliases at all.

`pnpm db:verify` then asserts what the model claims: browse by country, filter by category
through a recursive CTE, alias resolution, and every invariant a trigger or constraint is
supposed to hold — including that an item committed without an `origin` country is
rejected. Its rejection tests run inside transactions that are rolled back, so the seed is
intact afterwards; the last line of output says so.

### Regenerating the country list

`backend/src/db/reference/countries.ts` is generated, not hand-edited:

```sh
cd backend && node scripts/generate-countries.mjs
```

## Domain documentation

`CONTEXT.md` holds the glossary — what an Item, a Category, an Origin and an Alias mean
here. `docs/adr/` holds the decisions and, more usefully, the options each one rejected.
Every table in `schema.ts` cites the ADR that shaped it.
